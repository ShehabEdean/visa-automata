Quick architecture (edit if theres a better alternate way)





Firestore – store each application as a document with fields: lastName, firstName, passportNumber, phone, email, paid or not paid yet visaType (first_demand, renewing, family_visit, affaire, …), notes, scanURLs (array of download links to the images).



Firebase Storage – upload the scanned pages; automatically get a public (or signed) URL to save in Firestore.



Firebase Auth – create accounts manually for you and your coworker (email/password). The static site can’t be seen without login.



Frontend – A single HTML file (or a few) with a search bar, a form to add new records + drag‑and‑drop image upload. Use the Firebase Web SDK (loaded from a CDN).

All of this stays within Firebase’s permanent free tier (Spark plan) for your scale.

How to build it (rough steps)





Create a Firebase project, enable Firestore, Storage, and Email/Password auth.



In the Firebase console, manually add two users (you and your coworker).



Write a simple index.html that includes the Firebase SDK scripts, a login screen, and a dashboard with:





An “Add Record” form



A search input that queries Firestore (e.g., where("lastName", ">=", searchTerm))



A table of results with links to open the scanned images



Push the static files to a private GitHub repository. Enable GitHub Pages – the site is public by URL but protected by the login screen.



You may also set a very simple passphrase in the HTML if you want an extra layer (not true security, but enough to stop random visitors from seeing the login form).



In short: For a free, two‑person or three, internet‑accessible paper‑management tool on GitHub Pages, use Firebase Firestore + Firebase Storage + Firebase Auth. It’s the closest you’ll get to a “local” feel while actually being usable by both of you
